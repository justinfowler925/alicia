# Alicia development contract

The accepted direction is one Alicia brain across surfaces, sessions and
protocols. Alicia is the chat-first home, with the existing Brutus workspace and Atlas on separate tabs.
Development runs locally. Studio is not a dependency. Corporate Vercel and
GitHub are future deployment and delivery targets, not prerequisites.

## Running development

`scripts/run-alicia-dev.py brain` runs the shared service on localhost:8794.
`scripts/run-alicia-dev.py web` runs the isolated Brutus development surface on
localhost:8789. Private configuration and state live under
`~/.brutus/alicia-development/`, outside Git. Use the project Python environment
and `PYTHONPATH=.` for these commands. Neither command changes the live Brutus
service on localhost:8768.

The three tabs are Alicia (`/`, with `/alicia` kept as an alias), Brutus (`/brutus`), and Atlas (`/atlas`). The Atlas page embeds the
existing configured Atlas interface; it does not start a second Atlas worker.
Anam renders Alicia using product-generated audio. The Brutus voice adapter
supplies transcription; replies are generated by the shared brain and spoken
with the configured Alicia ElevenLabs voice. No Anam model answers separately.

## Shared brain boundary

`brutus/alicia_brain.py` owns authenticated principal identity, persistent
conversation turns, explicit preferences, bounded cross-session recall and
feedback. Each surface credential maps to a principal and surface on the
server. A request cannot select a different principal. All history, memory,
feedback and idempotency queries are principal-scoped.

Brutus keeps a display mirror of its turns and retains its tool execution and
approval gates. A tool request travels back to its originating surface; only
that surface may return the result. Central memory tools execute in the shared
brain. Reusing a conversation id resumes its central history on another
authorized surface. Client timeouts never switch to an independent model.

Protocols implemented: native turns HTTP API, nonstreaming OpenAI-style chat
with an explicit `X-Alicia-Session-Id`, and the MCP stdio adapter
`python -m brutus.alicia_mcp`. MCP requires `ALICIA_BRAIN_URL` and
`ALICIA_SURFACE_TOKEN`. Streaming chat completions are rejected explicitly.

The development model adapter explicitly selects Claude CLI with its own
tools disabled. An HTTPS model API is supported by setting
`ALICIA_MODEL_PROVIDER=openai-compatible`, `ALICIA_MODEL_BASE_URL`,
`ALICIA_MODEL_API_KEY`, and `ALICIA_MODEL`. Model selection is explicit and
there is no automatic provider fallback.

## Cloud migration boundary

This is a local development service, not a Vercel production deployment.
The current durable repository uses SQLite and requires persistent disk.
Before Vercel deployment, move storage to a managed transactional database,
replace local development credentials with corporate authentication and
server-held surface grants, and select a funded model API. Never place SQLite
in Vercel's ephemeral function filesystem and call it durable.

Keep surface URLs and secrets in environment configuration. GitHub should own
review, immutable build identities, evaluation suites and release checks;
Vercel should host the web/API deployment against the managed database. The
voice provider's WebRTC session remains independent of the API host. Existing
Nucleus is not migrated by this change: corporate viewer permissions need a
proper identity adapter before its users can share this service.

## Recursive improvement boundary

Justin authorized automatic promotion of changes that pass agreed tests.
The first implemented step is specific feedback attached to completed central
turns, partitioned into conversation, organization and presentation. Feedback
does not itself rewrite a prompt, model, permission or voice.

An acceptable promotion loop must freeze the accepted evaluation set and
baseline, generate a versioned candidate, evaluate it independently, enforce
hard regressions (identity isolation, grounding, tool authority, continuity,
interrupt/end behavior), compare quality and latency, and retain the previous
version for rollback. Candidates must not rewrite the tests used to judge them.
The agreed quality thresholds, baseline population, candidate-generation
worker and automatic promotion/rollback executor are not implemented yet.
No Turing-level quality or continuous self-training claim is made.

## Verification

`tests/test_alicia_brain.py` checks cross-surface and protocol continuity,
principal isolation, persistence, request idempotency, tool settlement,
feedback and provider failures. `tests/test_alicia_api.py` checks preservation
of Brutus home, separate pages, avatar credential handling, request origin,
and central feedback persistence before acknowledgement.

`scripts/verify-alicia.cjs` exercises the live development pages in a hidden
browser. `ALICIA_LIVE_PROOF=1` additionally starts the actual provider avatar
and checks a model-generated answer and the audio presentation path. Physical
microphone acoustics and a real user's interruption experience require a live
conversation; synthetic input is identified separately.

## Conversation repair

The transcript and composer are always visible, alongside the presenter on
wide screens. Microphone permission is requested from the Talk gesture; video
connects independently and has its own retry. Denied microphone access is
reported explicitly instead of silently switching voice transports. Muting
spoken replies does not mute the microphone on the Alicia page.

ConvAI's opening message is empty and its output is muted as soon as the SDK
creates the session. Its tool callback cannot initiate a second product turn.
All audible answers use the configured Alicia TTS voice; avatar output is
routed through an audio context unlocked by the user's click, with the video
element itself muted for reliable autoplay.

The live browser check now requires measurable returned avatar audio and
advancing video frames, not just a “speaking” UI label. Recovery verification
in `scripts/verify-alicia-recovery.cjs` covers denied microphone permission,
video failure independent of the microphone, output-only muting, and duplicate
tool prevention with a stubbed transport. Physical microphone and speaker
behavior in the user's browser remains a separate live check.

## Primary workspace and composer

Alicia occupies the main left column with the existing supervisor session
counts directly below her. Conversation remains visible on the right. The
readback and thinking mirrors are suppressed on this page; replies appear
once in the transcript.

The composer uses a single-line input, attachment control on the left, and
one Send/Stop control on the right. Attachments currently accept readable
text, Markdown, CSV, JSON and source-code files (five files, 25,000 characters
per file, 50,000 combined). Binary documents, PDFs, and images are explicitly
rejected rather than silently ignored. Selected file contents reach the shared
brain; the displayed user turn shows filenames instead of duplicating file
contents. Stop interrupts playback and cancels delivery of the current
central turn. An already-running model request may finish in the provider.

`verify-alicia-composer.cjs` checks attachment submission, stop behavior,
left-column placement, counter visibility and responsive single-line controls
using stubbed request responses. Central cancellation isolation and prevention
of late answers are covered by the shared-brain tests.
